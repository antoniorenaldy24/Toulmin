## 1. Product Identity & Architecture Overview

### 1.1 Identity

**Toulmin — The Self-Calibrating Claim Ledger** is a writing-time claim-verification workbench for scientific authors. It is named after Stephen Toulmin's argument model, *claim → data → warrant → qualified conclusion*, and maps every checkable claim of a manuscript onto that structure:

| Toulmin element | Product element | Produced by |
|---|---|---|
| **Claim** | Atomic claim extracted from one clause of one sentence of the author's manuscript | L0 clause partitioner + L1 Stage 1 |
| **Data (grounds)** | Verbatim evidence span from the cited reference: its abstract, its open-access full text, a PDF the author added, or a photographed printed source | L0 BM25 candidate selection + L1 Stage 2 `s01_evidence_span`, validated by the L0 anchor validator |
| **Warrant** | Micro-reasoning of at most 40 words linking the evidence to the claim | L1 Stage 2 `s03_micro_reasoning`, checked for reasoning↔verdict consistency by L0 |
| **Qualifier / conclusion** | Calibrated verdict + provenance + confirmation state | L1 `s04_verdict` → L3 policy → L2 confirmation |

**Single promise** (used verbatim in the video, the README and onboarding): *"Know which of your claims your sources actually support — while you write."*

**Positioning.** Toulmin is for authors checking **their own** manuscripts. It is not a peer-review tool for other people's manuscripts.

### 1.2 Core thesis

1. **On-device model.** It does high-frequency, zero-network, zero-marginal-cost structural work on every sentence: claim decomposition, check-worthiness triage, evidence alignment, and manuscript self-consistency decisions.
2. **Cloud model.** It does low-frequency, high-knowledge work: adjudication of a claim against its evidence with Google Search grounding, and discovery of alternative sources.
3. **Trust is measured, not assumed.** How far each local output is trusted is decided by measurement:
   - calibration (R1-E) decides whether local contradiction hints may appear (Path A or Path B);
   - the CF-1 test decides whether each local task is `authoritative` or `advisory`;
   - a separate support gate decides whether on-device "supported" verdicts may be shown at all.

   Proof mode shows these measurements.

### 1.3 M-U Adaptive-Threshold architecture

**M-U ("Unified Adaptive-Threshold")** means that Path A and Path B are two states of one routing policy. The state is selected **per profile** from measured calibration and distributed through Firebase Remote Config (`routing_table`).

- **Path B** is the always-on floor. No local accusation is surfaced. Local work is alignment, triage, uncited-claim detection (B4) and self-consistency (B5). Contradiction verdicts come only from L2 or from deterministic L0 rules.
- **Path A** is the calibrated ceiling. A local `CONTRADICTS` may surface as an unconfirmed **hint**. A hint never turns red without L2 confirmation.

Layers:

| Layer | Role | Calls a language model? |
|---|---|---|
| **L0** | Deterministic engine: parsing, normalization, citation scanning, clause partitioning, BM25 selection, chunking, sanitization, anchor validation, B5 pairing, reducer, Coverage Meter, gates | Never |
| **L1** | On-device inference through the Firebase AI Logic SDK: Chrome built-in Gemini Nano (Web), AICore Gemini Nano (Android), Apple `SystemLanguageModel` through `HybridModel` (iOS) | Yes, on device |
| **L2** | Cloud adjudication through the Firebase AI Logic SDK in `ONLY_IN_CLOUD` mode with `gemini-3.8-flash` | Yes, in the cloud |
| **L3** | Policy: decides which local verdict classes are surfaced and with what authority, from the Remote Config routing table and the on-device Calibration Probe | Never |

All four Firebase AI Logic inference modes are used, each where it fits:

| Mode | Used for |
|---|---|
| `ONLY_ON_DEVICE` | All local stages on capable devices, in both privacy modes; every check of the Android Pocket Ledger |
| `PREFER_ON_DEVICE` | Local stages on Web devices without a usable model, only after consent class A |
| `PREFER_IN_CLOUD` | *Find alternative sources*: cloud with Google Search when online; on-device ranking of the cached library when offline |
| `ONLY_IN_CLOUD` | L2 adjudication (`l2Adjudicate`, `l2AdjudicateProvided`) |

### 1.4 The three clients

| Client | Device(s) | Role |
|---|---|---|
| **Web Chrome Workbench** (`apps/web`) | PC Ryzen 7, MacBook M5, Lenovo ThinkPad (Chrome desktop) | **Primary platform.** Editor, Claim Ledger, Coverage Meter, evidence inspector, consent sheets, Proof mode, import and export, whole-manuscript audit |
| **Android Pocket Ledger** (`apps/android`) | Xiaomi 15T Pro | **Offline mobile companion.** Distributed only as the `bundledSample` flavor. It runs strictly offline on the bundled Sample Manuscript ledger and its bundled evidence cache. The author may also open local files chosen through the operating-system file picker or share sheet; these are processed entirely on the device. Every check runs through `Firebase.ai(...)` in `ONLY_ON_DEVICE` mode. The build makes zero Firebase network calls |
| **iOS Thin Client** (`apps/ios`) | iPhone 13 Pro Max (iOS 26, no Apple Intelligence) | **Fallback demonstration only.** A single "Check this claim" flow on `HybridModel(primary: SystemLanguageModel.default, secondary: Gemini)`. On this device the SDK falls back automatically to the cloud secondary model after consent class A |

**Android offline flows.** In Airplane Mode the Pocket Ledger promises only what it can verify on the device:

| Flow | What it does |
|---|---|
| **O1** | Re-check waiting claims against cached full text |
| **O2** | Resolve a claim from a photographed printed table row or page ("Select-row") |
| **O3** | Resolve a claim from a photographed typed or printed lab note |
| **O4** | Suggest citations for uncited assertions from the cached library |

Every printed-source result needs two author confirmations against a crop showing the row and its column header:
1. the values were read correctly;
2. **"This row supports my claim"** — the row entails the claim.

A lab-note result is never shown as a contradiction. Anything that needs the network is labelled as unavailable in this build.

**Local-only persistence (D-10).** Each device stores its ledger only on that device. Nothing is synchronized between devices, and no device sends manuscript text or ledger entries to the server for storage.

### 1.5 Scope of "while you write" (normative)

**Single-file documents** get live checking as the author types. These are:
- a blank document;
- one `.md` file;
- one `.tex` file without `\input`, `\include` or `\subfile`;
- the built-in **Sample Manuscript**.

Single-file documents are editable. They offer "Download source", request `navigator.storage.persist()` on the first edit, and warn before the tab closes if there are changes that have not been downloaded. The Sample Manuscript is editable so that an author or judge can type a new claim and watch it being checked.

**Imported multi-file projects** (`.zip` LaTeX project archives and `.docx` files) open as **read-only audit copies**:
- the author keeps editing in their own editor and uses **Re-import** to refresh;
- results are reconciled by the content key `resultKey`, so unchanged claims keep their results;
- Re-import accepts any multi-file kind;
- every ledger row deep-links `file:line` into the original source.

The import screen shows this sentence exactly: *"Multi-file projects open as a read-only audit copy: keep editing in your own editor and re-import to refresh."* The README states the same scope next to the single promise.

### 1.6 Non-Goals (MUST NOT be implemented or claimed)

1. **Peer review of other people's manuscripts.** No peer-review assistance for third-party confidential manuscripts.
2. **No generative privacy paraphrasing.** No generative anonymization, redaction, generalization or paraphrasing of manuscript text "for privacy" before cloud use (D-09).
3. **No unmeasured latency claims.** No "sub-second" claim, and no latency figure that was not measured on the named device.
4. **No overclaiming of accuracy.** No "no false alarms" claim. No "verified" or "guaranteed" claim for any local output. No green "Supported" for any on-device support verdict that has not passed the support gate (D-08, D-29).
5. **No in-place editing of audit copies.** Imported multi-file projects (`.zip`, `.docx`) are not edited inside Toulmin. There is no round-trip export back into Word or LaTeX files, and no multi-author co-editing.
6. **No native macOS target.** The MacBook M5 runs the Web build in Chrome (D-23).
7. **No cross-device cloud ledger sync.** There is no cloud sync and no device-to-device transfer of ledgers, keys or results. Each device keeps its own local ledger (D-10).
8. **No autonomous rewriting** of the author's text.
9. **No false uniqueness claims.** Do not claim that no other tool verifies claims against full text, or that no other tool assesses a manuscript's citations with a language model.
10. **No unsupported hybrid features.** None of these is designed into a hybrid path: Gemini Live API, embeddings, on-device PDF, audio, video or image generation, server prompt templates. Firebase AI Logic **template-only mode MUST NOT be enabled**, because it blocks every request that does not use a server prompt template, hybrid requests included.

### 2.2 Agent loading contract (MUST)

1. **Load this file first.** Load `AGENTS.md` in full at the start of every task, before any other specification file.
2. **Then load the minimum files.** Load the files named for your task in §2.3. Load another specification file only when your task touches a symbol owned by that file (§2.1). Load only the section that defines the symbol, not the whole file.
3. **Never reconstruct a rule from memory or from code.** If a rule you need is not in a loaded file, load its owning file. Existing code is not evidence of the specification.
4. **The owning document wins.** If two specification files disagree, the owning document wins (§2.1). The agent records the conflict in its pull-request description and does not resolve it by guessing.
5. **Locked decisions bound everything.** No document, issue, comment or code review may re-open a decision in §5. A change that contradicts a decision MUST NOT be merged.
6. **Exact copy is exact.** Every string marked *exact* in a specification file is stored once in `packages/copy/en.json` and rendered unchanged. `copy.test.ts` compares the stored strings with the specification.
7. **Conformance first.** A change to any L0 algorithm, reducer or gate MUST come with updated golden files in `conformance/l0/`. TypeScript and Kotlin MUST produce identical outputs on every golden file. Swift MUST produce identical outputs on the subset it implements (`norm`, `segment`, `anchor`, `reducer`).
8. **Freeze tiers are enforced.** Files listed in `/freeze/tier_a.txt` and `/freeze/tier_b.txt` change only under the rules of D-30. The pull-request description states which tier, if any, the change touches.
9. **Acceptance rows are the definition of done.** A task is complete only when every acceptance row of `docs/spec/07_EVAL_SPIKES_AND_ACCEPTANCE.md` that names the changed module passes.

## 3. Normative Conventions, Evidence Labels & `VERIFY-AT-SPIKE` Contract

### 3.1 Normative keywords

The keywords **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** are used as defined in RFC 2119. A requirement marked MUST is a build-breaking acceptance criterion.

### 3.2 Evidence labels

Every factual statement that is not a design decision carries exactly one label:

| Label | Meaning |
|---|---|
| `[F]` | **Primary fact.** Official documentation, the official contest rules, a peer-reviewed paper, or a first-party team measurement. The source MUST appear in the reference list of the document that uses it, or be named inline. |
| `[F2]` | **Secondary fact.** A reputable secondary source or vendor page. Product-comparison rows labelled `[F2]` MUST be re-verified against the vendor's own page before they are published in the README. |
| `[I]` | **Strong inference.** Derived by arithmetic or reasoning from labelled facts. The arithmetic is shown. |
| `[A]` | **Unverified assumption.** It MUST be verified by the named spike before anything relies on it. |
| `[H]` | **Testable hypothesis.** Measured by the evaluation suite of `docs/spec/07_EVAL_SPIKES_AND_ACCEPTANCE.md`. |
| `[UNVERIFIED]` | A literature claim whose primary source could not be located. It MUST NOT appear in the video, README, Devpost text or UI. It is kept only as design motivation. |

Only figures labelled `[F]` may appear in the video and README, and only exactly as worded in `docs/spec/08_CONTEST_README_AND_VIDEO.md`. No other problem statistic may be invented.

### 3.3 `VERIFY-AT-SPIKE` contract

Some SDK symbol names, parameter names and platform behaviours cannot be confirmed from documentation alone. They are marked inline as:

> `⚠ VERIFY-AT-SPIKE <ID>: <what to check> → <fallback if false>`

Rules:
1. **Both paths, behind a flag.** Every marker names exactly one spike or backend check. The agent MUST implement the primary path **and** the stated fallback behind a feature flag named `spike_<id>_primary` (boolean; for example `spike_s_l2_primary`). The flag defaults to the fallback until the spike passes.
2. **Record the result.** The spike result is recorded in `/docs/spikes/<ID>.md`, with the measured values and the device, browser or SDK versions. The flag value follows from that record.
3. **Pre-decode markers resolve in Phase 0.** A marker that governs pre-decode behaviour (anything that changes what a model receives; the Tier A list in D-30) MUST be resolved before the Tier A freeze. If its spike has not passed by then, the fallback becomes the permanent behaviour for the frozen package.
4. **Other markers resolve before Phase 3.** Every other marker MUST be resolved before Phase 3 begins. If its spike has not passed by then, the fallback is adopted.
5. **One path ships.** When a marker is resolved, the losing path is kept only if the specification says it is a runtime fallback (for example the L2 text-JSON path). Otherwise it is deleted together with its flag.
6. **Complete list.** Every marker in the specification names a spike in the register below or a backend check `BE-1`–`BE-5`. A marker naming anything else is a specification defect.

### 3.4 Identifier, unit and parameter conventions

1. **Artifact identifiers are opaque names.** Version-like suffixes in artifact identifiers — `p2.1` (prompt set), `probe_set_p2.json`, `porter_v1.json`, `TriageV1`, `VerdictV1`, `B5CheckV1`, `O2PhysicalExtractV1`, `AltSourcesV1`, dataset files ending in `_v2` — are frozen names of artifacts. They are not document versions. Use them verbatim.
2. **Money.** All amounts are US dollars, written `US$60`.
3. **Daily quotas** reset on the **Asia/Jakarta calendar day**. The client shows the reset time in the user's local time.
4. **Durations** are written with units (`250 ms`, `20 s`, `72 h`). Configured durations are stored in milliseconds in Remote Config.
5. **Environment parameters.** Every time-bounded behaviour reads an environment parameter, never a literal date:

   | Parameter | Meaning |
   |---|---|
   | `JUDGE_TIER_EXPIRY_EPOCH` | Unix epoch seconds after which judge claims expire and judge codes stop granting the judge pool. It MUST be later than the end of the official judging period. Free, unrestricted test access on the base URL MUST stay available at least until this time |
   | `MONITORING_MODE` | `STANDARD` or `ACTIVE_JUDGING`; selects the operator runbook cadence (D-12). It is set by an operator and read by alerting configuration only, never by client code |

6. **Hashes.** `sha256hex(x)` is the lowercase hexadecimal SHA-256 of the UTF-8 bytes of `x`. Concatenation inputs use `"|"` as the separator unless a definition says otherwise.

| **D-01** | **Name.** The product name is **Toulmin**. The tagline is *"Toulmin — The Self-Calibrating Claim Ledger"*. |
| **D-02** | **Quiet escalation of NEI.** A local `NEI_SILENT_ESCALATE` verdict MUST NOT display any warning colour, underline or interrupting message. The claim shows a progress chip and is counted in the Coverage Meter bucket `waiting` (escalation possible) or `unverifiable` (no escalation possible). It is escalated to cached full text first and then, with consent class B, to L2. An on-device `CONTRADICTS` that shows no value, negation or direction difference from the claim is treated exactly like NEI (`NO_DIFFERENCE_SIGNAL`, D-15). Only two things may interrupt the author: (1) **deterministic reference problems** — a DOI that no index matched **and** that the `doi.org` handle registry reports as not existing (`DOI_NOT_FOUND`), a retracted reference, or a key not found for an **explicit** citation marker (`\cite` family, Pandoc key, `.docx` field code, or numeric marker with a known bibliography order); and (2) a contradiction, shown as a hint (Path A, unconfirmed) or red (L2-confirmed). Cohen's κ is measured on a purely stratified 45-pair subsample (15 per class) drawn from the 140 non-`S-GRAY` pairs; the 10 `S-GRAY` pairs are labelled by annotator A2 **outside** that subsample and reported separately. ## 7. Strict Coding Agent Guardrails

Each guardrail is a MUST. Each is enforced by the CI check named in brackets; a failing check blocks merge.

### 7.1 Pure-function isolation of `packages/core-l0`

1. `packages/core-l0` contains **pure functions only**. It MUST NOT import Firebase, any DOM API (`window`, `document`, `navigator`, `localStorage`, `IndexedDB`), `fetch`, `XMLHttpRequest`, `WebSocket`, Node `net`/`http`/`https`/`fs`, timers used for scheduling, or any random source other than an injected seed. [`ci-ts.yml`: `no-restricted-imports` and `no-restricted-globals` on `packages/core-l0/**`]
2. Its outputs depend only on its inputs and the frozen data files it ships (`norm_table.json`, `unicode_15_1.bin`, `porter_v1.json`, `wordlist_en.txt`, `bm25_min_cov.json`). It is imported by the Web workers and by `functions/src/oa/chunk.ts`, so client and server chunking are byte-identical.
3. The Kotlin port (`apps/android/core-l0`) and the Swift subset (`apps/ios/ToulminCore`) are held to the same purity rule and MUST match `conformance/l0/*.json`. [`ci-android.yml`, `ci-ios.yml`]
4. The reducer is commutative and order-independent; property tests permute event order. [`prop/reducer.prop.test.ts`]

### 7.2 Single allowed import boundary for Firebase AI Logic

1. Only these modules may import or call Firebase AI Logic (`firebase/ai`, `com.google.firebase.ai.*`, `FirebaseAI`):

   | Platform | Allowed module | Contents |
   |---|---|---|
   | Web (and the Web evaluation runner) | `packages/firebase-client` | `src/l1/*` (on-device and hybrid: readiness, download, model singletons, call, deadline, settle, session cache) and `src/l2/*` (cloud: `l2Adjudicate`, `l2AdjudicateProvided`, *Find alternative sources*, grounding) |
   | Android | `apps/android/l1` | Tier cascade, `CallL1`, `@Generable` schemas, prompt loader |
   | iOS | `apps/ios/ToulminL1` | `AppleL1`, `HybridModel` session, text-JSON path |

   [`ci-ts.yml`: `no-restricted-imports` on `firebase/ai` outside `packages/firebase-client/**`; Android: Gradle module visibility; iOS: SwiftPM target dependencies]
2. `apps/web`, `apps/android/app` and `apps/ios/ToulminApp` consume these modules only through their exported interfaces. UI code never constructs a `GenerativeModel`.
3. Each `GenerativeModel` configuration is a singleton per `(mode, schema, reasoningCap)` (D-21). No sampling parameter is ever set.
4. In the Android `bundledSample` build, `apps/android/l1` uses `InferenceMode.ONLY_ON_DEVICE` exclusively, and no other module links Firestore, Functions, Authentication, App Check, Remote Config or Storage. [network-capture acceptance row; dependency check in `ci-android.yml`]
5. `functions/src/oaparse/**` MUST NOT import any HTTP client, Secret Manager client or Firebase Admin SDK. [`ci-functions.yml`]
6. Only `packages/core-l0/src/gate.ts` and its Kotlin port `Gate.kt` decide Path A, support-verdict authority and task authority, in clients and in `publish_routing.ts`. [`conformance/l0/gate.json`, `support_gate.json`, `holm.json`]

### 7.3 Regular expressions and the L0 watchdog

1. No L0 regular expression may contain a nested unbounded quantifier (for example `(a+)+`, `(a*)*`, `(a|aa)+` with overlapping alternatives, or `(.*)*`). Every pattern is linear-time on adversarial input. [`fuzz/redos.test.ts`]
2. The citation scanner and every scanner over manuscript text run in linear time.
3. Every L0 job runs in a worker under the **250 ms** watchdog (`packages/core-l0/src/watchdog.ts`; D-27). On expiry the worker is terminated and restarted and the input is marked `PARSE_TIMEOUT`. B5 work is split into per-metric-class jobs.
4. No L0 code blocks the UI thread.

### 7.4 No hardcoded dates, secrets, prompts or copy

1. **No calendar dates in code or configuration.** Expiry and time windows come from environment parameters (`JUDGE_TIER_EXPIRY_EPOCH`, `MONITORING_MODE`) or from stored record timestamps. [`ci-ts.yml`: lint rule rejecting ISO-date and epoch literals outside `/conformance` and `/eval-harness/fixtures`]
2. **No secrets in the repository or in any client artifact.** API keys of bibliographic services, `JUDGE_CODE_PEPPER` and `NET_HASH_PEPPER` live only in Secret Manager, each bound to exactly one service account. Judge codes are never committed; only their HMAC document IDs are uploaded by `tools/issue-judge-codes.ts`. [`tools/scan-artifacts.ts`; IAM binding check in `ci-functions.yml`]
3. **No App Check debug token or debug provider** in any release configuration or distributed build, with no exception (D-18). [`tools/scan-artifacts.ts`]
4. **Prompts and schemas are read only from `packages/prompts/p2.1` and `packages/schemas`.** Builds copy them into app assets with their SHA-256. At runtime each app compares the asset hash with Remote Config `prompt_version` and refuses to run L1 on a mismatch (`PROMPT_HASH_MISMATCH`). Kotlin `@Generable` property names and order MUST equal the JSON Schemas. [`schemas/tools/check-kotlin-mirror.ts`; schema/prompt hash check in `ci-ts.yml`]
5. **User-facing strings** come only from `packages/copy/en.json`. [`copy.test.ts`]
6. **Grounded text and links are never persisted** — not in IndexedDB, Room, SwiftData, Firestore, Storage or logs. Only the verdict and the anchored quote from Toulmin's own evidence are stored. [acceptance rows on grounding persistence]
7. **No production API keys, project secrets or personal data** in Testing Instructions, README, video or logs.

### 7.5 Security and infrastructure invariants

1. No public HTTP function exists in production. Every client-callable function is a callable with App Check. `oaParse` and `oaParseJudge` have `invoker` set to `oafetch-sa` only and run as `oaparse-sa`.
2. No Serverless VPC Access connector is provisioned.
3. Content Security Policy and Trusted Types are served exactly as specified in `05`. `index.html` contains only the hashed inline bootstrap, which defines the Trusted Types policies `default`, `toulmin-html`, `toulmin-worker` and `toulmin-loader`. CSP reporting endpoints exist only in the staging project. [`tools/csp-hash.ts --verify`]
4. Client IPs for per-network limits are taken only from the `X-Forwarded-For` entry appended by Google's front end, never the client-controlled left-most entry, and are stored only as `netHash` with `NET_HASH_PEPPER`.
5. Firestore and Storage rules are tested on the emulator for every change. [`ci-rules.yml`]

### 7.6 Change discipline

1. A pull request that changes a file listed in `/freeze/tier_a.txt` after `l0-freeze-a` fails CI unless it carries the label `tier-a-refreeze` and re-runs every affected evaluation (D-30).
2. A pull request that changes a file listed in `/freeze/tier_b.txt` after the first benchmark run MUST include the committed replay report `eval-harness/reports/replay/{runId}_{tierB}.md` and state whether it corrects an objective defect or applies a DEV-motivated fix.
3. A pull request that changes a file listed in `/freeze/cf1_baselines.txt` after the first CF-1 run fails CI.
4. Replay determinism is tested with the network disabled. [`ci-ts.yml`]
5. Public wording follows the honesty rules: never "no false alarms", "verified", "guaranteed" or "sub-second"; on-device results are never called "supported" unless D-29 (1) or (2) holds; the on-device role is described exactly as *"reads the candidate passages from the cited paper and decides which one answers the claim"*.
